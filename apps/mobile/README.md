# @daak/mobile

The React Native app shell (iOS + Android) driving the in-process
`DaakEngine` TurboModule from `packages/core`.

## Canonical commands

Run from the repo root. `cargo` needs `export PATH="$HOME/.cargo/bin:$PATH"`.

### Runs and verified here

```bash
pnpm --filter @daak/mobile test        # jest, 15 suites / 178 tests
pnpm --filter @daak/mobile typecheck   # tsc --noEmit
pnpm --filter @daak/ui test            # jest, 6 suites / 10 tests
pnpm --filter @daak/ui typecheck
pnpm --filter @daak/platform test      # vitest, 9 files / 54 tests
pnpm --filter @daak/platform typecheck
pnpm --filter @daak/core typecheck
pnpm turbo typecheck test              # what CI runs (see .github/workflows/ci.yml)
cargo test -p daak-ffi                # controller runs the workspace suite
```

`@daak/core`'s vitest run includes a `daakd` socket contract suite that needs
bind permission; in a restricted sandbox it fails 12 tests with
`Operation not permitted`. That is an environment limit, not a code failure.

### Recorded, NOT run in this environment (no toolchain present)

```bash
# Android — needs Android SDK + NDK + a Gradle-capable JDK, and ./gradlew is present
cd apps/mobile/android && ./gradlew :app:assembleDebug

# iOS — needs full Xcode and CocoaPods
cd apps/mobile/ios && pod install
xcodebuild -workspace Daak.xcworkspace -scheme Daak -configuration Debug \
  -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' build

# Android share-target smoke, needs a device or emulator with Daak installed
adb shell am start -a android.intent.action.SEND -t text/plain \
  --es android.intent.extra.TEXT "hi" -n dev.darshit.daak/.share.ShareTargetActivity

# Codegen for the TurboModule specs (writes generated sources; run after a
# spec change, before a native build)
pnpm --filter @daak/mobile codegen
```

There is no `lint` script anywhere in the workspace: the root `lint` script only
forwards to `turbo run lint` and no package defines a `lint` task, so
`pnpm lint` is a no-op. Do not record it as a gate.

Schemes that actually exist: `Daak` and `DaakShareExtension`
(`apps/mobile/ios/Daak.xcodeproj/xcshareddata/xcschemes/`). `Daak.xcworkspace`
does not exist yet — it is generated by `pod install`, which has never run here.

## Prerequisites / not verified in this environment

- **No full Xcode.** `xcode-select -p` = `/Library/Developer/CommandLineTools`,
  so `xcodebuild` errors before doing anything. No `pod` on PATH.
- **No Android SDK/NDK.** `ANDROID_HOME`/`ANDROID_SDK_ROOT` unset,
  `~/Library/Android/sdk` absent, no Gradle installed. Only `adb` is present.
- **No iOS/Android devices or simulators**, so no app was installed, launched,
  or driven.

**Native builds and device runs were NOT executed in this environment.** Every
Kotlin and Swift file in `apps/mobile/` and `modules/` is source-level only: it
has never been compiled, and the `src/__tests__` pins that read those files are
text assertions, not compile or runtime checks. The `daak-ffi` bindings were
checked against real `uniffi_bindgen` output, which proves the surface matches
the crate — not that the app links or launches. Two known consequences on a
real host: the UniFFI xcframework/modulemap for `import daak_ffiFFI` is still
missing, and the generated Android bindings look for `uniffi_daak_ffi` while
the cdylib is `libdaak_ffi.so`, so `engine.start()` will raise
`UnsatisfiedLinkError` until packaging ships the `.so` per ABI.

The device matrix in [`e2e/README.md`](e2e/README.md) is entirely unchecked.
Item 1 (QR pairing) is structurally blocked: nothing on the FFI surface calls
`Engine::offer_pairing`, so the host half of pairing cannot complete.
